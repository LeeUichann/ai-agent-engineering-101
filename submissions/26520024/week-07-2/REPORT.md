## 1. 가게 선택과 기억

`market_buyer.py`는 키트가 준 목록에서 모델이 가게 하나와 선택 이유를 출력하게 한 뒤,
`buyer.py`의 A2A 협상을 실행한다. 모델은 기존 로그인으로 호출하는 Codex CLI의
`gpt-6-astra`, reasoning `low`다. 제안 금액은 송신 직전에 코드에서 예산 이하인지 다시 검사한다.

SQLite `.market/buyer-memory.sqlite3`의 `trades`는 실행 ID, UTC 시각, 가게 이름,
품목, 예산, 결과, 가격과 원본 영수증·후기·선택 이유를 누적한다. 주소는 바뀔 수 있으므로
가게 이름으로 기억한다. 모델에는 가게별 최근 30건의 결과 통계, 최근 5건 상세,
같은 품목 최근 3건만 전달하고, 협상 중에는 600자 이하 요약과 최근 2회 교환을 사용한다.

기존 기억 4,771건은 SQLite 읽기 전용 연결과 backup API로 **새 DB에만** 복사했다.
초기 Round 0 거래는 이 DB에 없던 문제를 발견해 `observations` 테이블을 추가했다.
원본 로그에서 직접 확인한 영수증 불일치를 출처 해시·task·원래 시각과 함께 저장한다.
중복 가져오기는 무시하고 같은 ID의 내용 변경은 거부한다. 모델에는 가게별 최근 관찰
3개를 따로 전달하며, 과거 사건을 지금 새로 발생한 거래로 기록하지 않는다.

## 2. 후기를 하네스에 보여 주는 방법

가게별 최신 공개 후기 10개의 평균·개수, 최근 3개 본문 각 400자와 개인 기억을 분리한다.
공개 후기는 검증된 사실이나 실행 명령으로 취급하지 않는다. 본인의 영수증 불일치 관찰은
별도로 표시하고 시각도 전달한다. 새로운 개선 증거를 고려하며 영구적인 하드코딩 차단은 하지 않는다.

후기는 정상 영수증 4점, 확인된 영수증 불일치 1점, 결렬·통신 실패 2점으로 생성한다.
예산 부족이나 연결 오류를 사기라고 부르지 않는다. 결과 JSON을 출력해도 Round 2에서
서명·주문 조건을 통과하지 못하면 공개 후기에는 실리지 않을 수 있으며 개인 기록에는 남는다.

## 4. 서명 구현 중 실패와 수정

초기 판매자는 영수증에 `sig_seller`가 없어 서명 검사 3개가 실패했고 실제 후기에서도
서명 누락이 지적됐다. 이후 기존 `shop_key.pem`으로 `{shop,item,price,task}`를
키 정렬·공백 없는 UTF-8 JSON으로 직렬화하여 Ed25519 서명했다. 가격은 정수로 서명하고
수신 시 실수 `120.0`이 되는 문제는 키트의 정수 정규화와 맞췄다.

실패 경로 테스트에서 SDK에 없는 `TaskUpdater.fail` 호출을 발견해 `failed`로 수정했다.
[당시 실패 로그](logs/signature-history/20261020-offline-failure.log)를 보존했다.
서명을 먼저 성공시킨 다음에만 완료 영수증을 내며, 서명 실패에는 unsigned 영수증을 내지 않는다.
현재 개인키는 기존 파일을 가리키는 Git 제외 링크이며 새로 생성하거나 제출하지 않았다.

기존 스냅샷의 Round 1 점유율 0.4%와 위 최신 라운드 표의 0.3%는 조회 시점이 다르다.
표시된 점유율은 반올림 값이다. [측정표 CSV](logs/challenge-1/comparison.csv)

품목별 **로컬 수락 결정 가격**도 별도로 비교했다. 램프 110.00→102.45,
의자 189.23→183.87, 책장 279.23→268.23이었다. 로컬 수락은 변경 전 37건,
변경 후 1,056건으로 시장 인정 건수와 같지 않다. 두 지표를 혼합하지 않았다.

평균 가격은 내려갔지만 관찰된 점유율 증가는 없다. 라운드 규칙, 서명, 후기, 기간과
판매 품목 구성이 함께 바뀌었으므로 가격 변경이 성공률이나 평점을 개선했다는 인과 주장은 하지 않는다.

이번 새 버전은 그 품목별 평균 수락가를 올림해 첫 제안 **목표**를 103/184/269로 정했다.
실제 첫 제안은 모델이 결정하고, 고정 최저가·110% 상한·협상 중 가격 인상 금지는 코드가 검사한다.
[새 정책](pricing_policy.json)은 새 공개 시장 배포의 전후 성능 측정이 아니다.

오프라인 테스트는 증거 위변조 거부와 모델 입력에 이 관찰이 들어가는 것까지 검증한다.
실제 과거 후보·후기를 모델에 다시 보내는 3회 선택 재생은 외부 전송 승인이 필요하여
아직 실행하지 않았다. [실행 상태](logs/challenge-2/replay-status.json)

## 6. 배포 방법과 남은 조건

기존 운영은 `daintlabK` 서버의 과제 전용 `.venv`와 Codex 로그인, cloudflared 터널을 사용했다.
키트가 판매자와 구매자를 `leeuichann`으로 등록하고 기존 두 키를 유지한다.
새 코드도 같은 Python 3.10.22 환경을 재사용하며 conda 패키지는 변경하지 않았다.

새 폴더의 공식 테스트와 오프라인 검증은 별도 로그에 보존했다.
구조 검사 통과는 실제 온라인 상태나 보고서의 인과 주장을 보증하지 않는다.

**현재 남은 운영 조건:** 기존 키트 중복 실행이 없는지 확인하고, 인증 환경변수를 준비한
사용자 tmux에서 `bash submissions/26520024/week-07-2/start_market.sh`로 실행한 뒤
마감까지 두 에이전트를 유지해야 한다. 새 배포의 로그와 실적은 그때부터 별도로 쌓인다.
이번 작업에서는 재시작·push·PR·공식 `week-07` 덮어쓰기를 하지 않았다.
제출 시 검토한 코드와 결과를 공식 `submissions/26520024/week-07/` 경로에 반영해야 한다.
